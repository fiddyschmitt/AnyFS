SharePoint as a source, in its three flavours: SharePoint Online, SharePoint Server on-premises and
SharePoint Embedded. Each shows a site's document libraries (or an application's containers) as a
folder tree that reads, writes and renames, on every mount AnyFS has.

**SharePoint Online** (`sharepoint-online`): a Microsoft 365 site, through Microsoft Graph. You sign
in once with your work or school account, in your browser (or with a device code on a machine
without one); the sign-in is kept in the source's secret store and renewed silently. Every document
library of the site is a top-level folder, or pin one library and serve just that. Small files are
spooled whole on open; large ones are read in ranges as the client asks, several at a time; writes
are uploaded when the file is closed, in one request up to 4 MiB and in 10 MiB pieces above that.
AnyFS ships its own app registration, so nothing has to be set up in your tenant beyond an
administrator's consent the first time; an organisation that prefers its own registration pastes
its client id into the settings.

**SharePoint Server** (`sharepoint-server`): an on-premises site, through SharePoint's REST API with
a Windows account over NTLM or Kerberos, reached by name or by address from any machine, domain
member or not, on Windows and Linux (macOS is untested so far). The same tree, caching and
write-on-close as Online. A file's times are set through the client object model, the one way
SharePoint Server takes them exactly; SharePoint honours them only for a site collection
administrator. Tested against SharePoint Server Subscription Edition and SharePoint Server 2019.

**SharePoint Embedded** (`sharepoint-embedded`): the containers an application keeps your files in,
through Microsoft Graph, each container a top-level folder (or pin one, by name or by id). Access is
the administrator's to arrange: they register AnyFS, or the owning application's client id goes in
the settings.

**Also in this release**

- Bulk copies into a slow upstream no longer re-list the folder for every file: the SDK's listing
  cache corrects one entry in place after a write.
- The SMB mount keeps a file open between the server's read requests, instead of opening it again
  for every piece. On a source where an open costs a round trip (SharePoint) a 200 MiB file came
  through at 2 MiB/s before and at full speed now; local sources are unaffected.
- The FUSE mount reads ahead per handle, as the WinFsp mount has since 0.1.0 (one shared piece of
  code now): the kernel asks for a file in 128 KiB pieces, each a round trip to a remote source, and
  the same 200 MiB SharePoint file that came through at 8 MiB/s reads at 32 to 36 MiB/s.
- Write-on-close sources behave under Windows: a file that is still being uploaded answers its own
  stats, reads and renames, so Explorer's copy, rename and attribute changes land in order.
- NTLM from Linux without the gss-ntlmssp plugin: the published builds use .NET's own NTLM.

**Tested**: unit suites on Windows; live suites against a Microsoft 365 developer tenant (Online as
an administrator, Embedded as a plain member) and SharePoint Server Subscription Edition and 2019
farms built as code in the test lab (`provisioning/sharepoint/README.md`); the end-to-end lab's
SharePoint rows, against both farms, on the Linux host over FUSE, SMB, WebDAV, FTP and HTTP from the
Linux, upstream and Windows clients, and on the Windows host over WinFsp, SMB, WebDAV, FTP and HTTP
from the local and upstream clients.

**Downloads**: one executable per OS, nothing to unpack: `anyfs-win-x64.exe`, `anyfs-linux-x64`,
`anyfs-linux-arm64`, `anyfs-osx-arm64` (Apple silicon) and `anyfs-osx-x64` (Intel); on Linux and
macOS run `chmod +x` on it first. `SHA256SUMS.txt` lists their sums.

**Not yet**: a macOS `.app` bundle, NFS, app-only sign-in for unattended hosts, delta queries and
SharePoint shortcuts.

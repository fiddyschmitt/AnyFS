SharePoint as a source: SharePoint Online (Microsoft 365), SharePoint Server on your own network
and SharePoint Embedded, all one source type (`sharepoint`). Paste the address and AnyFS works out
which it is: a site under `.sharepoint.com` or `.sharepoint.us` is SharePoint Online, any other
address is SharePoint Server, and a container type's id is SharePoint Embedded. Each shows a site's
document libraries (or an application's containers) as a folder tree that reads, writes and
renames, on every mount AnyFS has. The Site URLs come first in the Add source dialog and name the
source for you ("contoso.sharepoint.com Team", with the path to match; several sites on one server
are named by the server) until you type a name of your own, also when you change them later, and the
settings show only the fields your address and sign-in need.

Every document library of a site is a top-level folder, and the site's subsites are in a Subsites
folder beside them, each named as its address ends and holding its own libraries and Subsites; or
pin one library and serve just that. With the tenant's root site as the address
(`https://contoso.sharepoint.com`), a Sites folder beside them holds every other site you can open
(`/sites/...`, `/teams/...`), found through SharePoint's search, each with its own libraries and
Subsites; a site wanted on its own can still be a source of its own.
Small files are spooled whole on open; large ones are read in ranges as the client asks, several at
a time; writes are uploaded when the file is closed.

**Several sites in one source**: give their addresses one per line, and each is a folder of its
own, named as its address ends, with its libraries and Subsites, under the one sign-in (a Windows
account reaches sites on several servers; the web session signs in to one). Handy where the
server's root site is closed to you but some sites are not. A subsite's address works as given, and
so does a library's, a page's or a folder's: AnyFS finds the site it is in. A site you may not open,
or one that is not there or not answering, is left out and the others serve: the source starts
within 15 seconds even with a server down, Test lists what was left out and why, and AnyFS tries
those sites again every few minutes, so one you are given access to later turns up by itself.
Give the server's root site among them and it is the source's own site: its libraries at the top,
and the other sites you gave in its Sites folder (site collections) or Subsites folder (subsites),
beside what it finds itself. Each site shows once, where its own place is: one the root lists
anyway, or a subsite of another site shown, is not repeated beside it. The addresses are kept in
alphabetical order.

**A site's pages** show in its Site Pages folder as Markdown, read-only: `News.aspx` is
`News.aspx.md`, the page's full address on its first line, then its title as a heading and its
text, lists, tables, links and pictures (by their addresses), converted from the page's HTML as
MarkItDown converts HTML (here by ReverseMarkdown, its .NET counterpart). A classic site's landing
page, `default.aspx` in the site's own folder, shows beside its libraries as `default.aspx.md`
(through the web session and a Windows account; Microsoft Graph cannot reach it). A library whose
title holds a character a file name cannot (`Health / Safety`) shows with its look-alike
(`Health ／ Safety`).

**Folders open at once, and stay current**: AnyFS keeps what it has seen of each SharePoint folder
and answers from it, so a folder opens without a round trip and a search tool reading many files at
once no longer makes AnyFS list the same folder again and again (in the lab, a 24-thread search of
a 5,000-file folder went from 108 files in ten minutes to 1,000 in 15 seconds). A folder listed
twice within five seconds, as pressing F5 twice in Explorer does, is fetched afresh, and a walk of
every site and folder in the background, at the start and every 30 minutes, brings in what changed
elsewhere. Both are in the source's advanced settings.

**Kind to SharePoint Online**: AnyFS sends a tenant at most 10 requests a second on average (up to
100 at once after a quiet spell), within Microsoft's published default of 3,000 in five minutes
for a user, and when SharePoint asks it to wait, every request waits. A 24-thread search of nine
sites and 15,000 files ran in the lab without being throttled or losing a file, where before it was
throttled nearly 200 times and lost one.

**Signing in** is a choice; Automatic picks for the address:

- **App sign-in** (SharePoint Online and Embedded): you sign in once with your work or school
  account, in your browser (or with a device code on a machine without one), and AnyFS works
  through Microsoft Graph; the sign-in is kept in the source's secret store and renewed silently.
  AnyFS ships its own app registration, so nothing has to be set up in your tenant beyond an
  administrator's consent the first time; an organisation that prefers its own registration pastes
  its client id into the settings.
- **Web session** (SharePoint Online), for when your organisation will not register an app: AnyFS
  opens Edge or Chrome with a profile of its own (never your everyday browser's), you sign in on
  Microsoft's page as you would to the site, and AnyFS works through SharePoint's REST API with
  that session, as the site's own pages do. A hidden browser renews the session in the background
  while your Microsoft sign-in lasts (with "Stay signed in", up to 90 days unless your organisation
  sets it shorter), so a window opens again only when Microsoft wants you to sign in. It renews only
  when the session has lapsed, not when SharePoint refuses you something you may not open (Online
  answers both alike), and never twice within two minutes. Where your
  organisation keeps AnyFS from the browser's remote debugging (Edge's RemoteDebuggingAllowed or
  UserDataDir policy), AnyFS signs in through Selenium WebDriver instead, with your default browser
  first and Firefox among the others; Edge or Chrome under such a policy is passed over, since its
  WebDriver needs the same remote debugging.
- **Windows account** (SharePoint Server): NTLM or Kerberos, with a user name and password or as
  yourself, reached by name or by address from any machine, domain member or not, on Windows and
  Linux (macOS is untested so far). **Windows account, as yourself** asks for nothing: AnyFS goes as
  you are signed in to Windows, a smartcard or Windows Hello sign-in included. When the server
  refuses the sign-in, Test says what it asks for and which account AnyFS tried; when it takes the
  sign-in but the account may not open the site (often the server's root site), Test says that,
  as whom.

Through the REST API (the web session and SharePoint Server) a file's times are set through the
client object model, the one way SharePoint takes them exactly; SharePoint honours them only for a
site collection administrator. SharePoint Embedded's access is the administrator's to arrange: they
register AnyFS on the container type, or the owning application's client id goes in the settings.

**The US Government cloud (GCC High)**: a site under `.sharepoint.us` signs in at Microsoft's US
Government endpoint and uses its Graph, chosen automatically; the Cloud setting overrides it, and
SharePoint Embedded goes by the tenant's domain. AnyFS's own app registration exists only in
Microsoft's global cloud, so there Automatic signs in with the web session; for an app sign-in your
administrator registers an app in your tenant: the Mobile and desktop applications platform with
the redirect URI `http://localhost` and public client flows allowed, the delegated Microsoft Graph
permissions User.Read, Files.ReadWrite.All and Sites.ReadWrite.All (User.Read and
FileStorageContainer.Selected for Embedded), and admin consent. Its client ID goes in the source's
settings.

**Also in this release**

- The WinFsp driver AnyFS installs is now WinFsp 2026 Beta 5 (2.2.26286), for a fix in its network
  provider: with WinFsp 2.1, on most PCs Explorer could not open `\\anyfs\<collection>` itself, and
  programs such as Paint could not open files there. With the beta both work. A PC
  with WinFsp 2.1 sees **Upgrade WinFsp driver** on the WinFsp mount: one click and an administrator
  prompt. AnyFS moves to the final WinFsp 2026 release when it comes out.

- An error serving one file stays with that file: the WinFsp mount handles 64 requests at once
  (it had one per processor) and logs what fails, and the SMB, FUSE and FTP mounts keep a failure to
  its request. A download that stops sending fails after a minute instead of waiting for ever, and a
  file whose download failed opens again.
- Bulk copies into a slow upstream no longer re-list the folder for every file: the SDK's listing
  cache corrects one entry in place after a write.
- "Count files on start" lists eight folders at a time on a remote source (SharePoint among them)
  instead of one, so the count finishes several times sooner; plugins can use the same walk
  (`TreeCount` in the SDK).
- The SMB mount keeps a file open between the server's read requests, instead of opening it again
  for every piece. On a source where an open costs a round trip (SharePoint) a 200 MiB file came
  through at 2 MiB/s before and at full speed now; local sources are unaffected.
- The FUSE mount reads ahead per handle, as the WinFsp mount has since 0.1.0 (one shared piece of
  code now): the kernel asks for a file in 128 KiB pieces, each a round trip to a remote source, and
  the same 200 MiB SharePoint file that came through at 8 MiB/s reads at 32 to 36 MiB/s.
- Write-on-close sources behave under Windows: a file that is still being uploaded answers its own
  stats, reads and renames, so Explorer's copy, rename and attribute changes land in order.
- NTLM from Linux without the gss-ntlmssp plugin: the published builds use .NET's own NTLM.
- A Microsoft sign-in refused for a settings reason (an unknown app or tenant, missing consent, a
  redirect URI the registration lacks) says which setting to fix, and the source stops instead of
  opening the sign-in page again every few minutes.
- A plugin's settings form can show only the fields that what has been entered calls for (the
  SharePoint source's address and sign-in decide its fields), and Test waits up to ten minutes for
  a sign-in in a browser window.
